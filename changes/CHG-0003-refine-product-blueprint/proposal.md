# Proposal

## 背景与问题

产品蓝图已经覆盖专业修谱端到端能力，但专家复核发现：能力地图单文件超过九百行；单一 `domain` 字段混淆产品责任与代码归属；家庭单元、账号访问、隐私生命周期和生态候选能力存在缺口；来源、权限、迁出和恢复能力出现过晚；V1.0范围过重；Capability、Roadmap和Product Spec存在少量不一致。

## 关联产品能力

本 Change 重构全部产品能力资产的表达方式，并重点新增或调整家庭单元、基础来源审核、账号访问、隐私、分阶段迁出、备份恢复、出版脱敏、机构运营和生态候选能力。

## 目标

- 将超大能力地图拆分为可定向读取的能力组文件；
- 区分业务、应用和平台能力，以及主责任领域与协作领域；
- 补齐产品能力缺口并消除版本依赖倒挂；
- 让 V0.1—V0.5 每个版本形成受治理、可迁移的纵向闭环；
- 将 V1.0 收敛为商用加固与真实项目验收；
- 为近期版本补齐验收、成功指标和核心风险；
- 通过确定性校验阻止未知引用、循环、版本倒挂和Roadmap缺项。

## 非目标

- 不设计页面、API、数据库表或代码模块；
- 不承诺 V1.1、V1.2 和 V2.0 候选能力的具体交付日期；
- 不改变现有六个领域的正式职责和 Context Map；
- 不实施任何业务功能。

## 范围与影响领域

影响 `product/` 正式产品资产、产品规划校验器、产品 Change 模板使用方式和全部六个业务领域的能力映射。领域不变量和代码布局不在本 Change 中修改。

## 关联 Decision

- `DEC-0004`：证据先于正式事实；
- `DEC-0005`：数据可迁移是产品底线；
- `DEC-0006`：每个版本交付受治理的纵向闭环；
- `DEC-0007`：产品能力责任不等同于代码归属。

## 风险

- 字段升级和文件拆分可能导致旧工具读取失败；
- 能力数量增加可能造成规划过度精细；
- 前置治理能力可能扩大 V0.x 范围；
- Roadmap与Capability若再次双写细节，仍可能漂移。

通过保留统一 Manifest、限制Capability粒度、只在Roadmap维护用户闭环，并增强自动校验降低风险。

## 成功标准

- 全部能力具有稳定ID、类型、责任领域、版本、承诺级别、状态、置信度和依赖；
- 能力依赖无未知引用、循环和版本倒挂；
- V0.1—V0.5均具备纵向闭环、非目标、验收、成功指标和风险；
- V1.0不再首次引入基础来源、授权、备份、审计和迁出能力；
- AI可以先读取Manifest和Release，再定向读取相关能力组；
- Repository Validation和回归测试全部通过。
