# Genealogy V2 · 中国式族谱管理系统

Genealogy V2 是一个面向中国式族谱场景的全新设计项目。

本仓库采用 **文档先行、领域先行、契约先行** 的建设方式。在产品范围、领域事实、业务命令、权限边界和验收标准稳定之前，不进入大规模编码。

## 项目边界

本项目与 `gyguan/genealogy` 相互独立：

- 不复制旧仓库业务代码；
- 不继承旧数据库表结构；
- 不兼容旧 API 作为设计前提；
- 不迁移旧 Git 历史；
- 旧仓库仅作为问题样本和产品经验输入，不作为实现模板。

可以借鉴的内容仅限已经证明有长期价值的原则，例如：

- 模块化单体优先；
- OpenAPI 契约驱动；
- PostgreSQL 与前向数据库迁移；
- 后端权限和隐私裁决；
- 正式事实经过审核后生效；
- 图谱只读取正式事实，不承担写入；
- 统一的页面结构、状态反馈和审计规范。

## 设计目标

Genealogy V2 不只是“画一棵家谱树”，而是建立一套能够表达、解释和审计中国式族谱事实的系统：

```text
谱系组织
  + 人物身份与多重归属
  + 家庭、伴侣与亲子关系
  + 历史事件、日期与地点
  + 来源、引文、主张与证据
  + 修谱命令、审核与正式生效
  + 权限、隐私与审计
  + 世系、家庭、组织三类图谱
```

## 当前阶段

当前阶段只建设高价值设计资产：

1. 产品范围与核心场景；
2. 领域模型与业务不变量；
3. 系统架构与模块边界；
4. 前端信息架构与设计规范；
5. API、数据库、权限和隐私规范；
6. 文档驱动的实施路线与验收门禁。

以下内容暂不进入仓库：

- 演示性质的业务代码；
- 未经验证的数据库建表脚本；
- 为完整而完整的接口清单；
- 不确定是否会使用的框架和基础设施；
- 从旧仓复制后再逐步修改的兼容层。

## 文档入口

文档基线将在 `docs/` 下维护：

```text
docs/
├── product/        产品范围、用户场景和领域模型
├── architecture/   系统架构、模块边界和关键决策
├── frontend/       信息架构、页面模式和视觉规范
├── standards/      API、数据库、权限与隐私规范
├── governance/     文档驱动开发与评审规则
└── roadmap/        实施顺序、验收门禁和发布路线
```

## 核心原则

1. **先定义事实，再设计表。**
2. **先定义业务命令，再设计写接口。**
3. **当前状态与历史事实分离。**
4. **证据记录与正式事实分离。**
5. **人物身份与谱系归属分离。**
6. **血缘、家庭和谱系组织关系分离。**
7. **权限范围与业务对象结构共同参与授权。**
8. **前端不推断正式业务事实。**
9. **不为旧实现保留永久兼容成本。**
10. **无法确认长期价值的内容不进入基线。**
