# 核心领域模型

> 状态：Review

## 1. 建模目标

领域模型必须能够准确表达以下问题：

1. 一个宗族如何组织为派、支、房，并在历史中发生变化？
2. 一个自然人如何拥有多个姓名、多个谱系身份和多种归属？
3. 家庭、伴侣、亲子、继嗣、出嗣和兼祧如何同时存在而不互相覆盖？
4. 不精确历史日期、历史地点和迁徙等事件如何记录？
5. 来源材料如何形成引文、主张和证据？
6. 候选主张如何经过审核转化为正式事实？
7. 当前结构、历史事实、系统版本和审计记录如何保持一致？

## 2. 限界上下文

```text
Identity & Workspace
  ├─ 用户、宗族空间、成员和工作上下文
  │
Lineage Organization
  ├─ 谱系组织单元、当前结构和历史演变
  │
Person Registry
  ├─ 人物稳定身份、姓名和外部身份链接
  │
Family & Kinship
  ├─ 家庭结合、伴侣和亲子关系
  │
Historical Record
  ├─ 历史日期、地点、事件和参与对象
  │
Evidence
  ├─ 来源、引文、主张、证据和争议
  │
Genealogy Culture
  ├─ 字辈、排行、堂号、家训和文化资料
  │
Change Governance
  ├─ 业务命令、提交、审核、执行和补偿
  │
Authorization & Privacy
  ├─ 角色、范围、隐私策略和审计
  │
Read Models
  └─ 档案、列表、统计、图谱、导入和导出视图
```

## 3. 核心对象

### 3.1 ClanSpace：宗族空间

`ClanSpace` 是协作、授权和数据隔离边界，不等同于血缘事实本身。

主要职责：

- 保存宗族名称、姓氏、堂号等工作空间信息；
- 管理成员、角色和默认隐私策略；
- 作为人物、来源、命令和审计记录的租户边界；
- 管理跨宗族人物引用和资料共享授权。

不变量：

- 每个正式业务对象必须归属且只归属一个宗族空间；
- 跨宗族对象不直接共享主键，只能建立受控链接；
- 删除宗族空间不能级联物理删除历史事实。

### 3.2 LineageUnit：谱系组织单元

用于表达派、支、房及其他经过批准的谱系组织层级。

建议属性：

- 稳定标识；
- 单元类型；
- 正式名称、别名；
- 当前上级；
- 当前状态；
- 有效历史期间；
- 可选的始迁祖、地域和说明引用。

当前父子结构只表示“现在如何组织”，历史变化由独立事件或关系记录表达。

不变量：

- 当前结构必须是一棵或多棵无环树；
- 父子节点必须属于同一宗族空间；
- 结构调整必须通过类型化组织命令；
- 移动节点时必须验证权限范围和子树冲突；
- 历史上的旧上级关系不得因当前结构变化而丢失。

### 3.3 Person：人物稳定身份

`Person` 只表示宗族空间内的稳定人物身份，不承担全部人物事实。

主要属性：

- 稳定标识；
- 基本性别或未知状态；
- 在世状态及其可信程度；
- 当前隐私等级；
- 生命周期状态；
- 外部人物引用。

不变量：

- 姓名不是人物唯一标识；
- 出生、死亡、职业、地址、墓葬等不应无限堆积在人物主表；
- 跨宗族可能是同一自然人的记录通过 `PersonIdentityLink` 表达；
- 人物合并和拆分必须保留来源、旧标识和审计关系。

### 3.4 PersonName：人物姓名

表达谱名、名、字、号、乳名、曾用名等。

关键属性：

- 姓名类型；
- 完整姓名与结构化组成；
- 使用期间；
- 语言或文字形式；
- 是否首选显示名；
- 来源和审核状态。

不变量：

- 同一人物可以有多个姓名；
- 首选姓名是显示策略，不意味着其他姓名无效；
- 姓名变更不创建新人物；
- 允许同名人物存在。

### 3.5 LineageMembership：人物谱系归属

表达人物以何种身份、通过何种原因、在什么期间归属于某个谱系组织。

关键维度：

- `membershipDimension`：血缘、谱籍、居住、管理或其他受控维度；
- `acquisitionReason`：出生、婚入、入继、出继、迁入、认祖等；
- `status`：候选、正式、结束、争议；
- 有效期间；
- 世次、字辈、排行等归属相关信息。

不变量：

- 一个人物可以拥有多个归属；
- 世次和字辈依附具体归属，而不是人物全局字段；
- 同一维度内互斥的归属由领域规则校验；
- 出嗣、入继等操作通过命令原子修改相关归属和亲子事实。

### 3.6 FamilyUnion：家庭结合

表达婚姻、伴侣、事实家庭或其他受控家庭结合。

`PartnerLink` 表达人物在家庭结合中的身份和期间。

不变量：

- 家庭结合不是两个人物间的简单对称边；
- 一个家庭结合可以有一个或多个伴侣记录，并支持历史变化；
- 伴侣关系不自动推出谱系归属；
- 婚姻事件、伴侣记录和家庭单元可以关联但不合并为同一对象。

### 3.7 ParentChildLink：亲子关系

表达父母、养父母、继父母、监护人、谱系父母等角色关系。

关键属性：

- 父母人物；
- 子女人物；
- 可选家庭结合；
- `parentRole`；
- 是否用于世系主线；
- 有效期间；
- 状态、来源和证据。

不变量：

- 父母和子女不能是同一人物；
- 正式世系主线必须防止祖先环；
- 生物亲子、收养亲子和谱系承继可以并存；
- 监护关系不自动进入世系图；
- 选择世系主线属于正式业务决策，必须审核。

### 3.8 HistoricalDate：历史日期

统一表达：

- 精确日期；
- 年月；
- 年份；
- 约略日期；
- 日期区间；
- 明确未知；
- 原始历法文本及标准化结果。

不变量：

- 不得用虚构的月日填补缺失精度；
- 原始文本和标准化值必须可以同时保留；
- 查询排序可以使用标准化边界，但展示必须保留原始精度语义。

### 3.9 Place：地点

表达历史地名、现代地理实体及两者间的映射。

不变量：

- 历史地名不能被现代行政区名称覆盖；
- 地点层级和现代映射允许不确定；
- 坐标是辅助信息，不是历史地点唯一事实。

### 3.10 HistoricalEvent：历史事件

统一表达出生、死亡、婚姻、迁徙、入继、出嗣、安葬、建祠等事件。

关键属性：

- 事件类型；
- 历史日期；
- 地点；
- 事件来源：人工记录、命令生成或导入；
- 参与人物、谱系组织、家庭单元和角色；
- 状态和证据。

不变量：

- 命令生成的事件只能由对应领域处理器创建或撤销；
- 事件参与对象使用类型化关联，不使用无约束通用目标；
- 一个事件可以存在多个相互冲突的候选主张，但正式事件结果必须明确。

### 3.11 Source、Citation、Assertion、Evidence

#### Source：来源

描述材料本身，例如族谱卷册、地方志、碑刻、档案、照片、口述或研究成果。

#### Citation：引文

描述来源中的具体位置、页码、段落、时间码、图像区域和原文摘录。

#### Assertion：主张

描述某个主体的某项候选事实，例如：

- 某人的谱名为某值；
- 某人物是另一人物的生父；
- 某支于某年从某地迁往另一地。

Assertion 必须使用类型化主体和类型化值模型，不使用任意 JSON 作为长期契约。

#### Evidence：证据关系

描述引文对主张的支持、反驳、中立或不确定关系，以及权重和解释。

不变量：

- 来源不等于事实；
- 引文不等于主张；
- 高可信证据也不能自动成为正式事实；
- 同一事实可以存在相互冲突的主张；
- 正式事实必须记录采用了哪个主张、通过哪个命令生效；
- 一个主张组最多有一个当前首选主张，且首选主张必须属于该组。

### 3.12 GenerationScheme、GenerationWord、GenerationAssignment

用于表达字辈方案及其在宗族或谱系组织中的适用范围。

不变量：

- 方案范围、指派方法和指派状态分别表达；
- 人物字辈落在具体谱系归属上；
- 自动匹配只能形成候选指派，不能直接覆盖人工审核结果；
- 不同支系允许存在不同字辈方案和偏移规则。

### 3.13 ChangeRequest、Review、Execution

#### ChangeRequest

保存不可变的命令类型、命令版本、规范化载荷、载荷摘要、提交人、提交范围和预期资源版本。

#### Review

记录审核任务、审核人、决策、意见、时间和职责隔离结果。

#### Execution

记录命令处理器版本、实际变更对象、执行结果、失败原因和补偿引用。

不变量：

- 提交后的命令载荷不可修改；
- 相同幂等键必须对应相同载荷摘要；
- 审核人不能是提交人；
- 审核权限和执行权限分别校验；
- 执行前必须重新校验资源版本和业务不变量；
- 已执行变更不通过删除审计记录回滚。

### 3.14 AccessGrant：授权范围

表达成员在宗族空间中的角色和资源范围。

首批范围类型：

- `CLAN`：整个宗族空间；
- `LINEAGE_SELF`：单个谱系组织；
- `LINEAGE_SUBTREE`：当前结构下的组织子树；
- `PERSON_SET`：明确人物集合；
- `RESOURCE`：特定来源、任务或导出对象。

结构调整时必须明确授权按照命令提交前、执行后还是二者交集进行裁决，禁止隐式选择。

## 4. 正式事实生效矩阵

| 候选内容 | 正式事实负责模块 | 生效方式 |
|---|---|---|
| 人物姓名主张 | Person Registry | 姓名新增/更正命令 |
| 谱系归属主张 | Lineage Organization + Person Registry | 归属建立/结束/转移命令 |
| 亲子主张 | Family & Kinship | 亲子建立/更正命令 |
| 伴侣或家庭主张 | Family & Kinship | 家庭结合命令 |
| 出生、死亡、迁徙主张 | Historical Record | 事件登记/更正命令 |
| 字辈主张 | Genealogy Culture | 字辈指派命令 |
| 组织沿革主张 | Lineage Organization | 拆分、合并、迁移、更名命令 |
| 继嗣、出嗣、兼祧主张 | Family & Kinship + Lineage Organization | 复合原子命令 |

Evidence 模块只管理候选知识和证据，不直接写入其他模块的正式表。

## 5. 三类图谱语义

### 5.1 世系图

- 核心边：被批准用于世系主线的亲子和承继关系；
- 不展示普通监护关系；
- 必须防环并限制深度、节点和边数量。

### 5.2 家庭图

- 核心节点：人物和家庭结合；
- 核心边：伴侣参与和亲子关系；
- 可以同时展示生物、收养、继养等角色差异。

### 5.3 谱系组织图

- 核心节点：谱系组织单元；
- 当前视图展示当前父子结构；
- 历史视图展示拆分、合并、迁徙、归属变化和有效期间。

三类图谱不能共用一个语义模糊的“关系边”模型。

## 6. 时间模型

系统必须同时区分：

| 时间 | 含义 |
|---|---|
| Historical / Effective Time | 事实在历史世界中发生或有效的时间 |
| System / Transaction Time | 系统何时记录、审核、执行或修正该事实 |

修正历史日期时，旧记录不能被静默覆盖，应保留系统时间上的变更轨迹。

## 7. 聚合与事务边界

推荐聚合边界：

- LineageUnit 当前结构调整；
- Person + PersonName 的身份维护；
- FamilyUnion + PartnerLink；
- 单条 ParentChildLink；
- HistoricalEvent + 参与对象；
- AssertionGroup + Assertions + Evidence；
- ChangeRequest + Review + Execution 生命周期。

跨多个聚合的继嗣、出嗣、兼祧和组织拆分命令由应用层协调，在单数据库事务中执行；不能把复杂业务不变量分散到前端或多个异步消费者中。

## 8. 明确禁止的模型

- `person.parent_id`、`person.spouse_id`；
- 单一 `person.branch_id`；
- 万能 `relationship(from, to, type)` 承载所有关系；
- 万能 `source_binding(target_type, target_id)`；
- 使用一个状态枚举统一所有领域对象生命周期；
- 使用 `before_json / after_json` 作为正式事实模型；
- 用软删除代替有效期间和历史事实；
- 用姓名、身份证号或外部文本作为内部稳定主键；
- 允许前端通过字段组合推导正式亲属关系。
