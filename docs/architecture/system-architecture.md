# 系统架构

> 状态：Review

## 1. 架构目标

系统架构服务于以下优先级：

1. 领域事实正确；
2. 变更可审核、可追溯、可补偿；
3. 权限与隐私可靠；
4. 查询和图谱性能可控；
5. 模块边界清晰；
6. 开发和部署复杂度适中；
7. 在真实需求出现后再演进基础设施。

不以微服务数量、框架数量或技术新颖度作为架构先进性的判断标准。

## 2. 总体形态

首期采用 **模块化单体 + 单 PostgreSQL 数据库 + 独立前端应用**。

```text
Browser
  → Web Application
  → HTTP / OpenAPI
  → Modular Monolith
       ├─ Identity & Workspace
       ├─ Lineage Organization
       ├─ Person Registry
       ├─ Family & Kinship
       ├─ Historical Record
       ├─ Evidence
       ├─ Genealogy Culture
       ├─ Change Governance
       ├─ Authorization & Privacy
       └─ Read Models
  → PostgreSQL
  → Object Storage（需要附件时再引入）
```

选择模块化单体的原因：

- 核心命令经常跨人物、关系、归属、事件和审核聚合，需要可靠事务；
- 团队和业务规模尚不足以证明分布式拆分收益；
- 领域边界可以先通过包、模块、接口和数据库访问规则落实；
- 后续只有在独立扩缩容、独立发布或组织边界出现时才考虑拆分。

## 3. 逻辑分层

每个业务模块内部遵循：

```text
Interface
  → Application
  → Domain
  → Port
  ← Infrastructure Adapter
```

### Interface

- HTTP Controller；
- API DTO 和错误映射；
- 身份与请求上下文解析；
- 不承载领域决策。

### Application

- 编排用例和事务；
- 调用权限服务；
- 加载聚合并执行命令；
- 协调跨模块原子业务操作；
- 发布进程内领域事件；
- 不直接拼写数据库 SQL。

### Domain

- 聚合、值对象、领域服务；
- 状态机和业务不变量；
- 类型化业务命令处理逻辑；
- 不依赖 Web、数据库或框架对象。

### Port

- Repository；
- QueryRepository；
- 时钟、ID、审计、文件存储等抽象；
- 只暴露当前模块需要的语义接口。

### Infrastructure Adapter

- PostgreSQL 持久化；
- OpenAPI、文件存储、指标和日志适配；
- 不向领域层泄漏 ORM Entity 或 SQL 行结构。

## 4. 模块边界

### 4.1 Identity & Workspace

负责用户、宗族空间、成员和会话工作上下文。

不负责谱系组织事实，也不根据 UI 菜单推断权限。

### 4.2 Lineage Organization

负责谱系组织单元、当前树、历史演变和人物归属的组织侧规则。

可以引用人物稳定标识，不拥有人物姓名和人物档案。

### 4.3 Person Registry

负责人物稳定身份、姓名、人物合并拆分和外部身份链接。

不拥有家庭关系、组织树或证据材料。

### 4.4 Family & Kinship

负责家庭结合、伴侣、亲子、承继及复杂复合关系命令。

不以谱系组织树代替亲子事实。

### 4.5 Historical Record

负责历史日期、地点、事件和参与对象。

命令生成事件必须受对应领域模块控制。

### 4.6 Evidence

负责来源、引文、主张、证据、争议和首选主张。

不直接修改其他模块正式事实。

### 4.7 Genealogy Culture

负责字辈方案、字辈词、指派规则以及堂号、家训等文化资料。

人物字辈结果通过人物谱系归属关联，不写回人物全局字段。

### 4.8 Change Governance

负责变更提交、审核、执行记录、处理器版本和补偿关联。

不包含具体业务不变量，实际执行委托给对应领域处理器。

### 4.9 Authorization & Privacy

负责角色、资源范围、字段级隐私、访问决策和审计策略。

业务模块必须调用它，但仍需执行自身对象状态和不变量校验。

### 4.10 Read Models

负责列表、档案、统计、图谱、导出等面向查询的模型。

只读取已生效事实和当前用户可见数据，不作为写模型事实源。

## 5. 依赖方向

允许：

```text
Interface → Application → Domain
Infrastructure → Port / Domain contracts
Read Models → 各模块公开查询视图
Change Governance → 各模块 Command Handler Port
业务模块 → Authorization Decision Port
```

禁止：

- 一个模块直接访问另一个模块的表；
- Controller 直接调用 Repository；
- Read Model 被业务写入流程反向依赖；
- Evidence 直接更新人物、关系或组织正式记录；
- Authorization 通过读取前端菜单状态决策；
- 公共 DTO 被当作领域对象在模块间传递。

模块协作优先使用：

1. 稳定标识；
2. 明确的应用服务或端口；
3. 进程内领域事件；
4. 专用只读投影。

## 6. 写入架构

正式写入统一经过：

```text
Request
  → Authentication
  → Command DTO Validation
  → Authorization: Submit
  → ChangeRequest Creation
  → Review
  → Authorization: Approve
  → Execution
  → Authorization: Apply
  → Version / Invariant Validation
  → Domain Transaction
  → Audit + Read Model Refresh
```

部分低风险草稿操作可以立即保存，但草稿不能被图谱、正式档案和对外导出当作正式事实。

正式写入要求：

- 类型化命令；
- 命令版本；
- 幂等键和载荷摘要；
- 预期资源版本；
- 明确作用范围；
- 不可变提交载荷；
- 处理器版本；
- 完整执行结果和审计。

## 7. 查询架构

写模型追求不变量和事务正确，读模型追求用途明确和性能稳定。

首期采用同库查询投影，不引入独立搜索集群或事件流平台。

查询类型：

- 对象详情；
- 条件分页列表；
- 当前组织树；
- 历史沿革；
- 人物中心关系；
- 三类图谱；
- 审核工作队列；
- 统计和导出任务。

所有大集合查询必须具备：

- 宗族空间过滤；
- 权限和隐私过滤；
- 稳定排序；
- 分页或硬上限；
- 深度、节点和边限制；
- 超限后的明确错误或截断标记；
- 可观察的耗时和结果规模指标。

## 8. 数据存储

### PostgreSQL

作为首期唯一结构化事实存储，承担：

- 事务；
- 外键和唯一约束；
- 递归查询；
- 版本和有效期间；
- JSON 仅用于扩展元数据或不可查询原始载荷，不作为核心事实模型。

### 附件存储

来源影像、照片和导出文件达到实际用例后引入对象存储。

数据库只保存：

- 业务元数据；
- 存储对象标识；
- 文件摘要；
- 隐私等级；
- 上传和扫描状态。

不把大文件直接存入核心业务表。

### 不首期引入

- Kafka 或其他消息平台；
- Elasticsearch；
- 图数据库；
- Redis 作为事实源；
- 工作流引擎；
- 分布式事务；
- 服务网格。

这些组件只有在存在可量化瓶颈和明确运维能力时才评审引入。

## 9. API 与契约

- 公共接口使用 OpenAPI 描述；
- 前端类型从契约生成，不手工复制 DTO；
- 写接口以业务命令表达，不暴露表结构 CRUD；
- 查询接口返回用途明确的读模型；
- API 不为旧仓库兼容而设计；
- 只有真实用例进入实施阶段时才补充对应契约，避免提前生成庞大空 API。

## 10. 权限与隐私执行点

授权至少执行两次：

1. 查询入口或命令提交时，判断用户能否发起操作；
2. 正式执行时，按最新结构、对象状态和资源版本再次判断。

读模型必须在后端完成：

- 行级范围过滤；
- 字段级隐私裁剪；
- 附件访问决策；
- 导出结果裁剪。

## 11. 一致性策略

### 强一致

适用于：

- 人物身份和姓名主状态；
- 当前谱系组织结构；
- 正式亲子和承继关系；
- 命令审核与执行状态；
- 权限授予和撤销；
- Assertion 首选结果。

### 可延迟刷新

适用于：

- 首页统计；
- 大型图谱投影；
- 搜索建议；
- 导出文件；
- 非关键聚合指标。

首期即使采用事务后刷新，也必须保留可重建方式，不允许读模型成为唯一事实源。

## 12. 可观察性

必须具备：

- 请求 ID；
- 当前宗族空间 ID；
- 命令和执行记录 ID；
- 结构化错误码；
- 慢查询和图谱规模指标；
- 权限拒绝和敏感访问审计；
- 导入、导出和命令执行耗时；
- 不记录密码、令牌、敏感人物字段和来源原文。

## 13. 演进触发条件

只有满足以下条件之一才讨论模块拆分或新基础设施：

- 某模块需要独立扩缩容且当前进程成为明确瓶颈；
- 独立团队需要不同发布节奏；
- 故障隔离有可量化收益；
- 单数据库事务不再是核心用例要求；
- 存储或查询特征与 PostgreSQL 明显不匹配；
- 团队具备新增系统的监控、备份、安全和运维能力。

在此之前，优先优化模块边界、查询模型和数据库设计。
