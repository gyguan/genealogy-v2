# 实施路线

> 状态：Review

## 1. 路线原则

Genealogy V2 按领域依赖和用户闭环推进，不按旧仓模块逐个重写。

实施遵循：

1. 先固化事实和不变量；
2. 先建设核心写模型，再建设公共读模型；
3. 证据核心早于人物、关系的正式证据绑定；
4. 类型化命令和审核早于批量写入；
5. 权限、隐私和审计不是收尾事项；
6. 前端在稳定契约和读模型上建设；
7. 导入、导出和数据工厂不能绕过正式生效路径；
8. 每一阶段必须形成可验证结果，不长期堆积不可见底层能力。

## 2. 阶段总览

```text
Phase 0  设计契约与工程护栏
  ↓
Phase 1  宗族空间与谱系组织
  ↓
Phase 2  来源、引文、主张与证据核心
  ↓
Phase 3  人物身份、姓名与谱系归属
  ↓
Phase 4  家庭、伴侣与亲子关系
  ↓
Phase 5  历史日期、地点与统一事件
  ↓
Phase 6  正式事实适配与复杂业务命令
  ↓
Phase 7  审核、执行、权限、隐私与审计
  ↓
Phase 8  V2 API 与公共读模型
  ↓
Phase 9  前端核心闭环与三类图谱
  ↓
Phase 10 导入、导出、数据工厂与发布门禁
```

## 3. Phase 0：设计契约与工程护栏

### 目标

建立可以约束后续实现的唯一权威基线。

### 交付物

- 产品定义；
- 领域模型；
- 系统架构；
- 前端设计系统；
- API、数据库、权限和隐私规范；
- 文档驱动交付流程；
- 首批 ADR；
- Issue 拆分和依赖图；
- 技术选型最小清单。

### 必须决策

- 人物跨宗族链接策略；
- 当前组织树存储策略；
- 历史日期结构；
- Assertion 类型化扩展方式；
- 正式事实生效矩阵；
- 命令信封、幂等和资源版本；
- 授权范围及结构变化裁决；
- 首期前后端技术栈。

### 门禁

- 权威文档达到 Approved；
- 不存在相互冲突的事实源；
- 首批实现 Issue 均可独立验收；
- 仓库中没有旧业务代码和未经验证 Schema。

## 4. Phase 1：宗族空间与谱系组织

### 用户结果

管理员能够建立宗族空间，并创建无环的派、支、房当前结构。

### 能力

- 宗族空间；
- 成员最小身份；
- 谱系组织单元；
- 当前父子结构；
- 历史结构记录基础；
- 组织查询和树上限；
- 组织范围标识。

### 门禁

- 同宗族空间外键；
- 防自引用和祖先环；
- 节点移动事务测试；
- 当前结构和历史事实分离；
- 当前树读模型可稳定排序和分页/限流。

暂不实现拆分、合并等复杂命令。

## 5. Phase 2：来源、引文、主张与证据核心

### 用户结果

采集员能够登记材料、引用具体位置并提出候选事实主张，而不会直接修改正式谱系事实。

### 能力

- Source；
- Citation；
- Assertion Group；
- 类型化 Assertion 基础；
- Evidence 支持/反驳关系；
- 首选主张；
- 来源和附件隐私元数据；
- 证据查询读模型。

### 门禁

- 来源、引文、主张和证据严格分离；
- 主张主体和值具备类型约束；
- 首选主张属于当前组且最多一个；
- Evidence 不能直接写正式事实；
- 敏感来源和附件访问有审计。

## 6. Phase 3：人物身份、姓名与谱系归属

### 用户结果

编辑能够建立人物稳定身份、维护多个姓名，并表达同一人物的多个谱系归属。

### 能力

- Person；
- PersonName；
- 首选显示名；
- 外部人物引用和身份链接；
- LineageMembership；
- 归属维度、取得原因和有效期间；
- 世次、字辈和排行的归属侧承载；
- 人物搜索和详情读模型。

### 门禁

- 姓名不是人物唯一标识；
- 不存在单一 `person.branch_id`；
- 首选姓名唯一；
- 多重归属语义清楚；
- 同一维度的互斥规则可验证；
- 人物详情按权限裁剪。

## 7. Phase 4：家庭、伴侣与亲子关系

### 用户结果

编辑能够建立普通家庭、生物亲子、收养和监护等关系，并明确哪些关系进入世系主线。

### 能力

- FamilyUnion；
- PartnerLink；
- ParentChildLink；
- 父母角色；
- 世系主线指派；
- 家庭详情；
- 世系和家庭查询基础。

### 门禁

- 不使用万能 Relationship；
- 家庭结合和伴侣边分离；
- 父母角色类型明确；
- 世系主线防环；
- 监护关系不自动进入世系；
- 关系变更具备来源和审核入口。

复杂继嗣、出嗣和兼祧放在 Phase 6。

## 8. Phase 5：历史日期、地点与统一事件

### 用户结果

编辑能够准确记录不完整历史日期、历史地点和出生、死亡、迁徙、婚姻等事件。

### 能力

- HistoricalDate；
- Place；
- HistoricalEvent；
- 类型化参与对象；
- 事件来源和状态；
- 历史时间与系统时间；
- 时间线和事件查询。

### 门禁

- 不虚构缺失日期；
- 原始日期文本可保留；
- 历史地名不被现代名称覆盖；
- 事件参与对象具备外键；
- 命令生成事件不能被普通接口任意修改；
- 双时间更正可追溯。

## 9. Phase 6：正式事实适配与复杂业务命令

### 用户结果

主张可以通过明确命令转化为正式事实；编辑能够安全处理组织沿革和中国式承继场景。

### 能力

#### 正式事实适配

- 姓名主张 → 人物姓名命令；
- 亲子主张 → 亲子命令；
- 归属主张 → 谱系归属命令；
- 事件主张 → 历史事件命令；
- 字辈主张 → 字辈指派命令。

#### 组织命令

- 更名；
- 移动；
- 拆分；
- 合并；
- 迁入、迁出；
- 终止和恢复。

#### 承继命令

- 入继；
- 出嗣；
- 继嗣调整；
- 兼祧；
- 补偿命令。

### 门禁

- 类型化命令；
- Dry Run 影响预览；
- 幂等键和载荷摘要；
- 预期资源版本；
- 单事务原子更新；
- 失败不留下半完成事实；
- 生成的事件、归属和亲子记录保持一致；
- 已执行命令只能通过补偿修正。

## 10. Phase 7：审核、执行、权限、隐私与审计

### 用户结果

主编和审核员能够按职责、范围和风险审核变更，系统在执行时再次验证权限和冲突。

### 能力

- ChangeRequest；
- 审核任务和状态机；
- 提交人/审核人隔离；
- 命令处理器注册和版本；
- SUBMIT / REVIEW / APPLY / COMPENSATE 权限；
- CLAN / SELF / SUBTREE / PERSON_SET / RESOURCE 范围；
- 在世人物字段裁剪；
- 敏感附件和导出策略；
- 审计追踪。

### 门禁

- 提交载荷不可变；
- 审核与执行分别鉴权；
- 结构命令覆盖源、目标和受影响子树；
- 权限撤销立即生效；
- 无权对象存在性不泄漏；
- 敏感访问、授权和正式变更有审计；
- 执行失败可重试或补偿，不伪装成功。

## 11. Phase 8：V2 API 与公共读模型

### 用户结果

前端和外部受控客户端能够通过稳定契约完成核心查询与命令闭环。

### 能力

- `/api/v2` OpenAPI；
- 人物、组织、家庭、来源、主张、审核读模型；
- 类型化命令接口；
- 统一错误、分页、权限和版本；
- 三类图谱接口；
- 契约生成和校验。

### 门禁

- 不暴露表结构；
- 不提供旧 API 兼容层；
- 前端生成类型无手工复制 DTO；
- 图谱具备深度、节点和边上限；
- 所有接口声明权限、错误和并发语义；
- 契约测试通过。

## 12. Phase 9：前端核心闭环与三类图谱

### 用户结果

用户可以使用统一原型风格完成建谱、修谱、审谱和查谱。

### 能力

- 应用外壳和宗族工作上下文；
- 首页；
- 建谱向导；
- 谱系组织；
- 人物档案；
- 家庭关系；
- 来源与证据；
- 历史事件；
- 审核中心；
- 世系图、家庭图、组织图；
- 成员权限和审计页面。

### 门禁

- 遵循统一页面模式；
- 不展示虚构数据和技术字段；
- 加载、空、错误、无权限和冲突状态完整；
- 1280–1920px 和移动端关键路径可用；
- 图谱有文本替代和截断提示；
- 权限与隐私以后端结果为准；
- 关键 E2E 闭环通过。

## 13. Phase 10：导入、导出、数据工厂与发布门禁

### 用户结果

团队能够批量构建演示和真实数据，安全导出谱书或结构化结果，并完成发布验收。

### 能力

- V2 导入模板和预览；
- 候选事实和变更请求生成；
- 权限裁剪导出；
- 谱书和结构化导出；
- SMALL / MEDIUM / LARGE 数据工厂；
- 复杂谱系、继嗣、争议证据和权限场景；
- 性能和发布门禁。

### 门禁

- 导入不直写正式事实；
- 导出冻结权限和策略快照并再次确认；
- 数据工厂与正式迁移脚本隔离；
- 大规模组织树、世系图、审核和导出性能达标；
- 空库部署、备份恢复、安全和审计验证通过；
- 所有 P0 业务不变量具有自动化测试。

## 14. 首批 Issue 建议

Phase 0 评审通过后，首批实现 Issue 只创建以下主题：

1. 工程骨架与模块边界测试；
2. PostgreSQL 测试基线与迁移门禁；
3. 宗族空间最小模型；
4. 谱系组织单元及防环；
5. 当前组织树查询；
6. Source / Citation 最小模型；
7. Assertion 类型注册与首选约束。

不要一次创建全部后续 Issue。每个阶段接近完成时，根据已验证事实细化下一阶段，避免提前锁死错误实现。

## 15. 进度判断

进度不以表数量、接口数量或页面数量衡量，而以可验证用户闭环衡量。

每阶段报告至少包含：

- 已形成的用户能力；
- 已固化的不变量；
- 已通过的测试；
- 未解决风险；
- 下一阶段依赖；
- 是否引入了待清理临时设计。
