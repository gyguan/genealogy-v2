# 文档驱动开发与评审流程

> 状态：Review

## 1. 目的

Genealogy V2 的复杂度主要来自领域语义、历史事实、证据、审核和权限，而不是页面或 CRUD 数量。

因此，项目采用文档驱动开发：

> 在编码前把问题、事实、边界、命令、契约和验收定义到足以被独立评审和验证的程度。

文档不是开发后的说明材料，而是设计和验收的输入。

## 2. 标准流程

```text
DEFINE
  → MODEL
  → CONTRACT
  → PLAN
  → BUILD
  → VERIFY
  → REVIEW
  → RELEASE
```

## 3. DEFINE：定义问题

输出内容：

- 用户和使用场景；
- 当前问题；
- 目标结果；
- 范围；
- 非目标；
- 业务术语；
- 验收标准；
- 主要风险和未知项。

完成标准：

- 能说明为什么需要该能力；
- 没有把实现方案误写成需求；
- 范围足以独立交付；
- 非目标清晰，避免静默扩大。

不满足时不得进入模型设计。

## 4. MODEL：定义事实和行为

输出内容：

- 涉及的领域对象；
- 事实源；
- 候选事实与正式事实；
- 状态及迁移；
- 类型化业务命令；
- 关键不变量；
- 时间语义；
- 权限和隐私影响；
- 失败、冲突和补偿方式；
- 读模型需求。

模型评审重点：

1. 是否复用了错误旧概念？
2. 是否出现万能关系、万能目标或万能状态？
3. 是否把页面字段当成领域事实？
4. 是否区分当前与历史、候选与正式？
5. 是否能够通过数据库和领域测试验证不变量？
6. 是否明确跨模块事务边界？

## 5. CONTRACT：定义契约

只为已批准用例设计契约。

输出可能包括：

- OpenAPI；
- 业务命令结构；
- 查询读模型；
- 错误码；
- 幂等和并发规则；
- 权限和字段裁剪；
- 数据导入导出格式；
- 进程内领域事件。

完成标准：

- 前后端和测试人员对语义理解一致；
- 不暴露表结构和内部实体；
- 错误、权限、分页和上限明确；
- 契约可自动校验。

## 6. PLAN：拆分实施

Issue 必须：

- 具有单一主要目标；
- 可以独立测试和验收；
- 列出依赖 Issue；
- 说明修改模块；
- 给出恢复或补偿策略；
- 说明不在范围内的内容；
- 不同时混入大规模模型、API、前端和迁移切换。

推荐拆分顺序：

```text
领域规则和数据库约束
  → 应用用例
  → API 契约与实现
  → 查询读模型
  → 前端页面
  → 集成和端到端验收
```

但一个用户切片可以在同一 Epic 下纵向交付，避免长期只有底层能力没有用户结果。

## 7. BUILD：实现

实现前检查：

- 权威文档状态是否允许实施；
- Issue 是否具备明确验收标准；
- 是否从最新默认分支建立独立分支；
- 是否存在未解决的关键设计决策；
- 是否确认没有复制旧仓代码。

实现要求：

- 修改范围与 Issue 一致；
- 领域规则变化同步测试；
- 公共 API 遵循 Contract First；
- Schema 使用前向迁移；
- 权限由后端执行；
- 不以 TODO、占位页面和虚假数据冒充完成。

## 8. VERIFY：验证

按风险分层：

### 单元测试

验证值对象、领域服务、状态机、权限策略和纯函数。

### PostgreSQL 集成测试

验证：

- 外键和约束；
- 递归防环；
- 乐观锁；
- 双时间；
- SQL 查询；
- 迁移；
- 事务和并发。

### 契约测试

验证 OpenAPI、请求响应、错误码和前端生成类型。

### 安全测试

验证跨宗族、范围、字段裁剪、附件和导出越权。

### 端到端测试

验证关键用户闭环，不追求每个按钮都由 E2E 覆盖。

### 性能验证

验证列表、组织树、图谱、审核队列、导入和导出的真实规模上限。

## 9. REVIEW：评审

### 领域评审

- 事实是否准确；
- 不变量是否完整；
- 复杂文化语义是否被过度简化；
- 正式事实生效是否可解释。

### 架构评审

- 模块边界是否被穿透；
- 是否新增无必要基础设施；
- 事务、一致性和补偿是否合理；
- 查询和写模型是否混用。

### 安全评审

- 授权入口和执行阶段是否都校验；
- 在世人物是否默认保护；
- 导出、附件和审计是否受控；
- 日志是否泄漏敏感数据。

### 前端评审

- 是否遵循页面模式；
- 是否只展示后端事实；
- 状态、冲突和权限反馈是否完整；
- 响应式和可访问性是否通过。

## 10. RELEASE：发布门禁

能力可以发布必须同时满足：

- 文档和实现一致；
- Issue 验收完成；
- 相关测试通过；
- PostgreSQL 迁移从空库验证通过；
- 权限和隐私用例通过；
- API 契约检查通过；
- 关键 E2E 通过；
- 监控、审计和错误码可用；
- 已知限制明确；
- 回退或补偿路径可执行。

## 11. 文档变更规则

### 小变更

不改变领域语义和公共契约的文字澄清，可直接在对应文档中修改。

### 设计变更

涉及以下内容时必须建立 ADR 或独立设计说明：

- 核心事实源；
- 聚合边界；
- 模块依赖；
- 数据库建模策略；
- 正式事实生效路径；
- 授权范围语义；
- 公共 API 破坏性变化；
- 新基础设施。

ADR 必须记录：背景、决策、替代方案、后果和替代条件。

### 被替代文档

不静默删除历史设计。将状态改为 `Superseded`，并指向新的权威文档或 ADR。

## 12. Issue 最小模板

```markdown
## 背景与问题

## 用户场景

## 范围

## 非目标

## 领域事实与不变量

## 方案与模块影响

## 权限与隐私

## 数据库与契约

## 失败、冲突和补偿

## 验收标准

## 验证计划

## 依赖关系
```

## 13. 完成定义

Issue 只有在以下条件全部满足时才能关闭：

- 目标用户结果已实现；
- 代码、契约、数据库和文档一致；
- 没有无关修改；
- 验收标准逐条验证；
- 风险和已知限制已记录；
- 必要的审计和指标存在；
- PR 已完成评审并合入；
- 不存在通过注释掉测试、降低门禁或保留临时兼容掩盖的问题。
