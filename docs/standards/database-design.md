# 数据库设计规范

> 状态：Review

## 1. 目标

数据库必须主动保护核心事实完整性，而不是只作为应用对象的持久化容器。

设计优先级：

1. 业务不变量可验证；
2. 当前事实和历史事实可追溯；
3. 权限范围和租户边界不串数据；
4. 查询性能有明确索引和上限；
5. Schema 可通过前向迁移安全演进；
6. 应用层与数据库各自承担适合的校验职责。

首期使用 PostgreSQL 作为唯一结构化事实存储。

## 2. 命名和标识

- 表名、列名统一使用 `snake_case`；
- 主键优先使用 UUID；
- 公共业务编码与内部主键分离；
- 外键字段使用明确名称，例如 `person_id`、`lineage_unit_id`；
- 不使用姓名、外部证件号或路径文本作为主键；
- 所有宗族空间内对象包含 `clan_space_id`，并参与关键唯一约束和索引。

## 3. 表的职责

一张表应有明确领域职责。

禁止将以下内容放入单个万能表：

- 所有亲属和组织关系；
- 所有业务对象状态；
- 所有来源绑定；
- 所有历史事件参与对象；
- 所有命令执行前后快照。

优先采用类型化表和外键：

```text
person_name
lineage_membership
family_union
partner_link
parent_child_link
historical_event_person
historical_event_lineage_unit
citation
assertion_person_name
assertion_parent_child
```

当不同类型共享生命周期和查询模式时，可以有公共头表，但类型化内容必须具备可约束结构。

## 4. 多租户和宗族边界

每个业务对象明确归属宗族空间。

数据库必须尽可能防止跨空间错误引用：

- 关键引用同时包含 `clan_space_id`；
- 使用复合唯一键和复合外键保证同空间关联；
- Repository 查询默认要求宗族空间；
- 管理员跨空间查询使用独立端口和审计；
- 不依赖应用“记得加 where 条件”作为唯一保护。

跨宗族人物链接使用独立 `person_identity_link`，不让一个 `person_id` 同时归属多个宗族空间。

## 5. 外键与完整性

核心事实默认建立外键。

不允许使用：

```text
target_type + target_id
subject_type + subject_id
object_type + object_id
```

来承担需要数据库完整性保证的核心关系。

可接受通用引用的场景仅限：

- 操作日志检索；
- 通知或搜索索引中的辅助定位；
- 不作为正式事实源的不可变审计元数据。

即使使用，也必须保存宗族空间、显示摘要和原业务记录标识，且不能反向用于领域写入。

## 6. 当前状态与历史事实

### 当前结构

用于高频业务判断和查询，例如当前谱系父子结构、当前首选姓名、当前有效归属。

### 历史事实

使用独立关系、事件或有效期间记录，不通过覆盖当前行丢失。

要求：

- 组织移动不能删除旧上级关系的历史；
- 归属结束记录 `effective_to`，不简单软删除；
- 正式事实更正保留系统版本和原命令引用；
- 软删除只表示技术生命周期，不替代业务历史。

## 7. 双时间语义

核心历史事实必须区分：

- `effective_from / effective_to`：事实在历史世界中的有效期间；
- `recorded_at / superseded_at`：系统记录和替代该事实的时间；
- `created_at / updated_at`：技术行维护时间，仅用于工程管理。

禁止使用一个 `created_at` 同时解释历史发生时间和系统记录时间。

历史日期不一定直接映射为 SQL `date`，应保存精度、约略、区间和原文。

## 8. 版本和并发

正式聚合包含单调递增版本号。

命令执行使用条件更新：

```text
UPDATE ...
SET version = version + 1
WHERE id = :id AND version = :expected_version
```

受影响行数不为 1 时返回版本冲突。

禁止通过锁住整个宗族空间解决普通并发问题。

组织拆分、继嗣等复合命令可以在明确范围内使用行锁，但必须：

- 固定锁顺序；
- 控制事务时长；
- 不在事务中调用远程服务；
- 提供死锁和重试测试。

## 9. 状态约束

每个领域对象拥有自己的受控状态，不使用一个通用状态字典覆盖全部对象。

数据库可以使用：

- `CHECK` 约束；
- 受控代码表；
- PostgreSQL enum，但只有状态极其稳定时使用。

优先使用可迁移、可扩展的文本代码 + CHECK 或代码表。

状态迁移由领域层控制，数据库负责拒绝明显非法值和结构。

## 10. 谱系组织树

当前组织结构可以采用：

- 邻接表作为事实源；
- 稳定路径或闭包表作为加速结构；
- 递归 CTE 查询和循环检测。

具体选型在实现前通过真实查询用例和 PostgreSQL 集成测试决定。

无论选型如何，都必须保证：

- 同宗族空间；
- 无自引用；
- 无祖先循环；
- 节点移动原子更新；
- 路径加速结构可以重建；
- 当前树与历史演变分离。

不要假设普通 `CHECK` 能跨行阻止递归环。

## 11. 人物和归属

- `person` 保存稳定身份和少量当前策略字段；
- `person_name` 保存多个姓名及使用期间；
- `lineage_membership` 保存多重归属；
- 字辈、世次、排行放在归属或专用指派表；
- 首选姓名和主要归属必须有唯一性约束或可靠事务规则；
- 人物合并不物理覆盖旧人物，应保存重定向和合并审计。

## 12. 家庭和亲子

- `family_union` 表达家庭结合；
- `partner_link` 表达参与人物和角色；
- `parent_child_link` 表达亲子角色；
- 是否进入世系主线使用明确字段或指派表；
- 祖先环需要应用校验 + PostgreSQL 集成测试，必要时使用事务内递归校验；
- 同一正式事实的互斥规则通过唯一索引、排除约束或领域事务实现。

## 13. 来源、引文和主张

- 来源、附件、引文、主张、证据分别存储；
- 引文必须引用真实来源；
- 证据必须引用真实引文和主张；
- 类型化主张使用专用值表或受控结构；
- 原始提取结果可保存 JSON，但正式可查询主张必须进入类型化结构；
- 首选主张必须属于同一主张组；
- 采用主张形成正式事实时保存正式事实、主张和执行命令的关联。

## 14. 命令、审核和执行

变更请求表至少保存：

- 命令类型；
- 命令版本；
- 规范化载荷；
- 载荷摘要；
- 幂等键；
- 提交人和宗族空间；
- 预期资源版本；
- 提交范围；
- 当前状态。

要求：

- 提交后载荷不可变；
- 幂等键在明确作用域内唯一；
- 相同幂等键和不同摘要产生冲突；
- 审核和执行记录追加写，不覆盖历史结论；
- 执行结果记录实际影响对象和版本；
- 补偿命令引用原执行记录。

## 15. 隐私数据

- 密码只保存强哈希；
- 令牌保存摘要或不可逆表示；
- 联系方式、详细地址、证件和敏感附件元数据明确分类；
- 需要时对高敏字段使用应用层加密或数据库加密方案；
- 加密密钥不存入仓库和数据库同一权限域；
- 普通查询视图不包含高敏字段；
- 导出和审计读取走专用查询路径。

## 16. 索引原则

每个索引必须对应明确查询或约束。

重点索引维度：

- `clan_space_id`；
- 当前状态和有效期间；
- 外键；
- 姓名规范化搜索字段；
- 谱系父节点和路径；
- 人物归属；
- 亲子父端和子端；
- 事件日期排序边界；
- 审核队列状态、审核人和提交时间；
- 幂等键和载荷摘要；
- 审计对象和时间。

避免：

- 为每个列机械建索引；
- 未验证的多列大索引；
- 在高频更新表上重复索引相同前缀；
- 使用 `%keyword%` 普通 B-tree 并误以为可命中。

## 17. 查询上限

数据库层和应用层共同限制：

- 分页大小；
- 递归深度；
- 图谱节点和边；
- 批量 ID 数量；
- 导入批次；
- 单次导出记录数；
- 附件数量和大小；
- 审核批量操作数量。

达到上限时必须返回明确结果，不静默截断。

## 18. Schema 迁移

使用 Flyway 前向迁移。

要求：

- 已进入共享环境的迁移文件不修改；
- 每个迁移聚焦一个可解释主题；
- 约束和索引命名稳定；
- 大表索引考虑锁和并发影响；
- 破坏性变化采用扩展、迁移、切换、清理步骤；
- 迁移脚本在真实 PostgreSQL 上执行集成验证；
- 禁止通过关闭 Flyway、修改 history 表或 `repair` 掩盖错误；
- 当前绿地阶段不提交未经验证的完整 Schema 草案。

## 19. 测试门禁

核心数据库设计至少验证：

- 同宗族空间外键；
- 唯一和互斥约束；
- 谱系组织防环；
- 世系主线防环；
- 首选姓名和首选主张唯一性；
- 幂等键与摘要冲突；
- 乐观锁冲突；
- 双时间更正；
- 权限范围查询；
- 大型递归和分页查询计划；
- 迁移从空库完整执行。
